# Find Together 完整 App 程序框架

## 1 项目定位
Find Together 面向家庭照护者，利用老人随身定位设备提供日常位置查看、异常核实、协作搜寻与寻回反馈。现阶段最合适的交付是保留原 UI 的 App Demo 与说明完整的工程框架。硬件尚未绑定不妨碍展示页面、事件流程、API 契约和 AI 生命周期；但硬件缺失并不是唯一未完成项，账户权限、地图服务、真实通知和模型评估也仍需实现。

这份工程以 Android 为暂定展示平台。App 将本地 HTML 装入 WebView，保留原有 19 个界面。后端和 AI 作为独立模块提供参考实现，当前并未与 App 自动联通。这样可以清楚解释每一层的责任，而不把模拟功能包装成完整上线能力。

“AI 智能预测”建议在材料中具体表述为“基于个体日常轨迹的时序异常检测”。LSTM Autoencoder 重建轨迹特征窗口，以重建误差衡量偏离；它没有直接预测未来位置，也没有给出经过校准的走失概率。

## 2 模块与责任

| 层级 | 模块 | 输入与输出 | 当前交付 |
| --- | --- | --- | --- |
| 定位设备 | GPS、时间、电量、连接状态 | 上传带设备标识的定位点 | 接口定义，未连接硬件 |
| App | 登录、绑定、位置、事件、社区 | 展示状态、提交家属决定与线索 | 原 UI 与 Android 离线展示壳 |
| 接入服务 | 设备鉴权、绑定、校验、去重 | 合法定位记录或质量错误 | API 设计；真实上报接口返回 501 |
| AI 服务 | 个体模型、特征窗口、误差 | 模型版本、分数、阈值、偏离等级 | 参考脚本；未训练、未部署 |
| 事件服务 | 核实、搜寻、核验、接应 | 可追踪事件状态 | Python 状态机与本机 Mock API |
| 协作服务 | 志愿者、线索、通知、协调 | 角色对应的事件信息 | 契约和页面演示 |
| 反馈服务 | 人工标签、审核、训练准入 | 经审核的正常样本 | 条件逻辑与再训练入口 |

### 数据流

```text
智能鞋 GPS + 时间 + 设备状态
          │  BLE 到附近网关，或蜂窝网络到服务器
          ▼
设备接入 → 格式校验与去重 → 原始轨迹存储
          │
          ▼
连续因果滤波 → 特征工程 → 每人滑动窗口 → 版本化 LSTM 模型
          │
          ▼
重建误差 + 阈值 + 数据质量 → 异常事件 → 家属核实
                                      ├─ 已安全 → 误报结案
                                      └─ 请求帮助 → 1 至 4 级搜寻
                                                    │
                                      线索 → 身份核验 → 家属确认 → 接回结案
          │
          └─ 恢复后 31 个连续正常窗口终点 → 请求人工反馈
                   → 人工审核的正常样本 → 候选模型 V2 → 评估 → 人工切换版本
```

AI 偏离等级与搜寻范围等级是两个概念，必须使用不同字段。模型误差较大，不等于一定走失，也不应直接触发扩大社区公开范围。搜寻发布、身份确认和接回等关键操作仍由家属或授权协调者决定。

## 3 角色和界面对应

| 角色 | 主要入口 | 信息范围与职责 |
| --- | --- | --- |
| 家属 | 设备、Alerts、寻回、反馈 | 查看关联老人的完整位置和事件，确认是否安全、是否求助 |
| 志愿者 | Community、线索、核验 | 仅查看参与事件所必需的信息，提交线索；不直接修改老人归属 |
| 协调人员 | 搜寻、线索处理、报警材料 | 协调搜寻、审核线索、帮助家属接应 |
| 模型维护者 | 后台评估与版本管理 | 只将审核过的样本加入候选训练集，评估后切换模型 |

原 HTML 中三个 onboarding 页面对应引导；one_click_login 与两个 sms 页面对应演示登录；01_home_device_binding 与 your_device 对应绑定和设备详情；03 至 06 页面对应告警、发布确认、雷达准备和分级搜寻；facial_scan、recovery_success、event_feedback 对应核验、寻回、反馈；三个 community 页面对应列表、详情、发布；police_report 对应报警协助材料。

离线 Demo 用预设数据，不创建真实账户。真实版本需要家庭邀请、设备归属核验、角色权限检查、会话失效和重复绑定处理，这些不能仅靠界面按钮实现。

## 4 硬件接入说明

建议的定位上报字段如下。以下标识和值是示例，不是用户数据。

```json
{
  "device_id": "demo-shoe-001",
  "subject_id": "demo-elder-001",
  "sequence": 42,
  "recorded_at": "2026-01-01T09:00:00+08:00",
  "lat": 30.0000,
  "lon": 110.0000,
  "accuracy_m": 12.0,
  "battery_percent": 86,
  "source": "gps"
}
```

设备应提供稳定标识、采样间隔、定位精度、时区明确的时间、电量和上报序号。服务器使用设备标识与上报序号防止重复接收；不能相信客户端自行声明的老人归属，必须查绑定关系。低电量、设备离线、定位不可用、旧数据补传和 GPS 跳点分别显示，不合并成“老人走失”。

BLE 只能将数据传到附近手机或网关。老人独自外出、家属手机不在身边时，需要随身网关或设备自身的远距离联网能力。文档提到的 ESP32 与 NEO-6M 组合不能单凭名称就视作已具备 4G 上报链路；实际硬件还需确认蜂窝模块、SIM、供电、天线和协议。

当前 `HardwareGateway.java` 仅定义配对、位置与错误回调。真正的厂商协议适配器没有实现，也未申请蓝牙、定位或摄像头权限。数据上传建议由有联网能力的设备或网关完成，不能假设家属 App 永远在后台运行。

文件名中的 normal 并不能证明每一条轨迹已经人工确认正常，也不能证明它是真实采集还是模拟生成。正式训练前需确认数据来源、所属个体与时区。检查到的“无空值、时间连续”只是结构质量结论，不是定位精度或算法有效性结论。

使用本轮参考预处理规则检查时，有效完整窗口为 10,071 个，规则未拒绝记录。这里的速度阈值和滤波参数尚未针对设备标定；没有被规则拒绝不代表不存在噪声或异常。

只有一周的正常数据，不能据此给出走失识别率、召回率或真实报警准确率。还需要单独留出的正常数据以及标注过的异常场景，包括改变路线、临时陪同出行、GPS 漂移和设备失联。

## 6 原 AI 代码的重要缺口与修正

| 发现 | 影响 | 本轮处理 |
| --- | --- | --- |
| 训练读 GPX，提供的是 CSV | 无法直接使用现有 CSV 运行原训练脚本 | 新入口明确接收 timestamp、lat、lon CSV |
| 文档检测使用每 10 秒一点的示例，CSV 每 60 秒一点 | 10 点窗口代表的实际时长不同 | 新实现固定 60 秒采样，不匹配则断开窗口 |
| threshold 写死在检测脚本，训练只打印 | 模型和阈值可能配错，日志删除后易丢失 | 清单保存阈值、schema、版本和校验值 |
| 卡尔曼 smooth 使用整段数据 | 对流式监测来说含未来观测，与在线条件不一致 | 共用只依赖过去与当前的因果滤波实现 |
| 纬度滤波器经 em 后用于经度 | 初始化和噪声参数复用不清晰 | 经纬度使用独立状态和相同显式参数 |
| 每次仅检测 10 点后退出 | 不存在真正连续的正常点计数 | 新增带时间去重的 Monitor 状态机 |
| “30+ 点后反馈”仅打印说明 | 不能在演示之外实际触发反馈规则 | 明确采用超过 30，即 31 个有效新窗口终点 |
| 先缩放全体数据、再对重叠窗口切验证集 | 校准与评估可能过于乐观 | 先按原始时间分段，各段单独构造窗口，scaler 只拟合训练段 |
| 同一训练集计算阈值 | 无独立阈值校准 | 60% 训练、20% 校准、20% 留出测试，仅作参考划分 |
| 反馈 CSV 缺失后仍访问 timestamp 列 | 原再训练分支可能报 KeyError | 再训练要求明确存在且有审核字段的反馈数据 |
| 更新模型没有版本成套约束 | 可能混用 V2 模型与 V1 scaler 或阈值 | model、scaler、manifest 按版本目录成套保存 |
| print 警报而没有事件与 API | App 无法获知可操作的状态 | 补充事件状态机与 Mock HTTP 契约 |

原文档中的“模型会更聪明”“再训练一定消除误报”“三个脚本绝不能合并”等说法不作为工程事实。再训练可能改善也可能退化，需要评估。三种任务可以属于同一工程甚至同一 CLI，但训练作业与实时服务应隔离执行。

当前特征仍为五个：平滑纬度、平滑经度、一天中的小时、星期、是否移动。这样方便对照原代码，但小时和星期在边界有跳变，后续可考虑周期编码；改变特征维度或顺序时必须重新训练和升级 schema，不可直接加载旧模型。

## 7 模型生命周期和产物

### 训练

指定某一人的正常 CSV → 校验顺序和坐标 → 按时间拆分 → 因果滤波和运动特征 → 拟合训练段 scaler → 10 点窗口 → LSTM Autoencoder → 独立校准段 99 分位阈值 → 留出正常段报警比例 → 保存候选版本。

10 个每分钟采样点的首尾跨度是 9 分钟，不是 10 秒或 100 个点。冷启动至少积累 10 个有效点才有第一个窗口结果。本版本只是文件回放参考，真正在线服务还需为每个老人长期保持滤波器与窗口状态，不能每收到一批数据就重置。

```text
artifacts/elder-demo/v1/
  model.keras             训练出的权重和模型结构
  scaler.json             五个特征对应的缩放参数
  manifest.json           阈值、模型版本、采样周期、预处理配置、文件校验值
  training_report.json    数据划分、质量拒绝数、训练损失、留出正常报警比例
```

这些模型文件未在本轮生成。`examples/demo_output.json` 是固定分数驱动的状态机演示，不属于上面的模型产物。

### 检测

加载一套版本目录 → 检查文件校验值和 schema → 相同预处理 → 模型重建 → MAE → 与成套阈值比较 → 输出模型版本、误差、阈值、偏离级别和反馈状态。异常分数不是概率。旧截图中的高分可能同时包含 GPS 尖峰、采样差异或缩放范围外输入，不能仅凭一个数值证明真实走失。

保留原思路中的 10 倍、50 倍、100 倍分界，便于对应原材料，但这些只是演示规则，尚未由验证集标定。高于基准、低于 10 倍的窗口也要有明确的 `deviation` 状态，不能遗漏。真实告警规则还应综合持续时间、数据质量和人工核实结果。

### 反馈和再训练

发生过异常 → 后续连续 31 个有效正常窗口终点 → 允许收集事件标签。一个新定位点至多使计数增加一次，重复时间戳不计入。遇到新的异常或数据质量断点重置计数。这个条件表示轨迹恢复正常，不表示老人已被找回；搜寻事件只能由明确的家属确认关闭。

反馈标签分为 `confirmed_normal`、`confirmed_incident`、`uncertain`。只有正常标签且人工审核通过的记录进入参考再训练入口。确认发生过危险的轨迹不能作为“正常”样本重新教给模型。

```text
timestamp,lat,lon,label,approved_by,approved_for_training
2026-01-01T09:00:00+08:00,30.0000,110.0000,confirmed_normal,reviewer-demo,true
```

V2 保存到新目录，不覆盖 V1；要在相同留出数据及独立异常场景上比较，再由维护者批准切换。旧版本保留用于回退。本轮提供再训练入口，但没有模型注册服务、自动部署或线上热切换。

## 8 事件状态与 API

```text
needs_review ─confirm_safe→ closed_false_alarm
needs_review ─publish→ searching ─report_clue→ verifying
searching ─escalate→ searching  （search_level 最高为 4）
verifying ─reject_clue→ searching
verifying ─confirm_identity→ awaiting_pickup ─confirm_pickup→ closed_recovered
```

| API | 状态 | 用途 |
| --- | --- | --- |
| GET /health | 已实现 Mock | 返回 mode 与 model_loaded |
| GET /v1/devices | 已实现 Mock | 返回一台演示设备 |
| POST /v1/demo/events | 已实现 Mock | 显式创建模拟事件，不伪装成模型检测 |
| GET /v1/events | 已实现 | 查询本地 SQLite 保存的事件 |
| POST /v1/events/{id}/actions | 已实现 | 校验状态后发布、升级、核验或关闭 |
| POST /v1/telemetry | 预留，返回 501 | 明确表示真实硬件入口未实现 |
| POST /v1/auth/session | 规划 | 登录与角色权限 |
| POST /v1/devices/{id}/bindings | 规划 | 设备归属核验与绑定 |
| GET /v1/subjects/{id}/locations | 规划 | 最近位置与历史轨迹 |
| POST /v1/events/{id}/clues | 规划 | 线索位置、时间、说明及必要附件 |
| POST /v1/events/{id}/feedback | 规划 | 人工反馈入库与审核 |
| POST /v1/model-jobs | 规划 | 离线训练任务和版本审核 |

实际后端数据库建议包含 users、family_members、subjects、devices、device_bindings、location_points、events、clues、feedback、model_versions、notification_deliveries。当前 SQLite 只保存演示事件；不能将设计表清单等同于全部数据库已经实现。

上线实现中需要事件版本号防止并发覆盖、幂等键防止重复提交、UTC 存储与本地时间展示，以及推送失败重试与送达记录。本轮本机单进程服务没有上述完整机制，也不提供远程访问入口。

## 9 Android Demo 如何保留你的 UI

Android 的 Activity 使用 WebViewAssetLoader 从应用 assets 读取相同 HTML、CSS、字体、图标和图片，不用截图替代可点击界面。原始 HTML 位于 `web-demo/pages`，打包副本位于 `android/app/src/main/assets/www`。重新改 UI 后运行 `tools/sync_android_assets.py` 同步两个目录。

App 内隐藏网页外框，以手机视口展示原页面。为了让硬件未接入时也能说明流程，配对、核验、报警与电话按钮显示明确的模拟反馈。App 不申请定位、蓝牙、摄像头和网络权限，不会运行真实模型。后端契约和 AI 代码保留为独立的后续接入层。

工程构建采用官方文档中的本地资源加载方式，但未进行 Android 编译、模拟器或真机测试。因此可交付“App Demo 源码与架构”，不能声称已经交付可安装 APK。

## 10 演示和验收清单

建议按三段讲解。第一段在原 UI 演示绑定、告警、求助和寻回。第二段打开本文件说明数据如何从硬件进入 AI 与事件服务。第三段查看 `examples/demo_output.json`，说明连续正常点、反馈资格与人工确认如何形成闭环，明确这是模拟得分。

已完成：19 页主体保留检查、外部素材本地化、19 项核心逻辑测试、CSV 结构与窗口检查、模拟输出生成。未完成：TensorFlow 真实训练、异常召回验证、流式服务联调、App 与 API 联通、APK 构建、手机显示验收、硬件连接、真实推送与身份核验。

后续顺序：确认被删产物和是否有模型备份 → 固定数据来源与采样协议 → 用独立数据验证 AI → 将 App 操作接到事件 API → 接硬件与定位质量处理 → 连接通知服务 → 最后做真实场景和设备验收。当前展示用途不必等待硬件完成，但应始终标明模拟边界。
